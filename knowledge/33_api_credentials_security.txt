TITLE: API CREDENTIALS AND APPLICATION SECURITY

PURPOSE:
To explain how to protect secrets, handle user authentication, and secure web applications and AI APIs.

WHAT IS IT?
Application security covers the practices and tools used to protect data, keys, and user accounts from unauthorized access or theft.

WHY IS IT USEFUL?
If you leak an API key on GitHub, attackers can steal your account and run up thousands of dollars in cloud bills within minutes. If you store plain-text passwords, any database leak compromises every user account. Security must be designed into an application from the beginning.

CORE CONCEPTS:

authentication: Verifying the identity of a user (verifying who you are).

authorization: Verifying what permissions an authenticated user has (verifying what you are allowed to do).

sessions: Temporary state stored on the server or in encrypted cookies to keep a user logged in across multiple requests.

password hashing: Converting a plain-text password into a one-way mathematical hash using secure algorithms like bcrypt or argon2. Never store raw passwords.

API key handling: Keeping secret keys out of source code by using environment variables.

secret storage: Storing secrets in environment variables or .env files that are ignored by version control.

encryption concept: Scrambling data so only someone with the secret key can decrypt and read it.

credential IDs: Referencing keys by internal identifiers rather than exposing raw key strings in the frontend.

user ownership: Ensuring that user A can only read, update, or delete records that belong to user A.

common security mistakes: Hard-coding secrets, committing .env files, trusting unsanitized user inputs, and missing authorization checks on API endpoints.

SIMPLE EXPLANATION:
Authentication is showing your passport at an airport gate. Authorization is having a boarding pass for Seat 14B—it lets you sit in that seat, but it does not let you into the cockpit. Environment variables are like a locked safe in your office; you keep your keys in the safe, never taped to the front door.

CODE EXAMPLES:

Loading API Keys from Environment Variables:
import os

Read the key from the operating system environment
api_key = os.getenv("OPENAI_API_KEY")

if not api_key:
raise ValueError("Missing OPENAI_API_KEY environment variable. Set it before running.")

Password Hashing with Werkzeug (Flask built-in):
from werkzeug.security import generate_password_hash, check_password_hash

When a user registers:
plain_password = "SuperSecretPassword123"
hashed_password = generate_password_hash(plain_password)

When a user logs in:
user_input = "SuperSecretPassword123"
is_valid = check_password_hash(hashed_password, user_input)
print("Login successful:", is_valid)

User Ownership Check in an API Route:
def delete_document(document_id, current_user_id):
# Always check both the item ID and the owner ID
doc = db.find_by_id(document_id)
if not doc:
return {"error": "Document not found"}, 404
if doc.user_id != current_user_id:
return {"error": "Forbidden: You do not own this document"}, 403
db.delete(doc)
return {"message": "Deleted successfully"}, 200

COMMON MISTAKES:

Hard-coding API keys directly inside Python or JavaScript files.

Committing .env files to Git repositories because .gitignore was missing.

Checking authentication without checking authorization (for example, verifying a user is logged in, but allowing them to view other users' private documents by changing an ID in the URL).

Using reversible encryption or simple encoding (like Base64) instead of cryptographic one-way hashing for passwords.

WHEN TO USE:
Implement environment-variable secret handling and ownership checks on every project that touches external APIs, user data, or databases.

WHEN NOT TO USE:
Do not create complex custom cryptography algorithms from scratch. Always use well-tested standard libraries like hashlib, werkzeug.security, or cryptography.

PROJECT CONNECTION:
In AI Creator Engine, user authentication protects the chat and generation endpoints. API keys for online providers (Gemini, OpenAI) are loaded from environment variables or encrypted settings, keeping credentials safe from browser exposure.
